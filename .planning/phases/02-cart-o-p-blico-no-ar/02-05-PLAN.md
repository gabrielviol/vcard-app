## Phase Goal

**As a** dono de um cartão digital, **I want to** ter meu cartão acessível publicamente em `/[slug]` e um QR pronto para circular, **so that** qualquer pessoa que escaneie ou receba o link veja meu cartão carregando rápido, sem cadastro e sem espera.

<objective>
Tira o backend do localhost. O `apps/api` passa a rodar em container no Render contra um Postgres Neon real, e um cron externo passa a mantê-lo acordado — fechando a segunda metade da mitigação de cold start (a primeira, o pré-aquecimento no save, está no plano 02-04).

Purpose: `PUB-04` existe porque `PUB-03` só cobre cartões que estão sendo editados. Um cartão impresso num adesivo há três semanas depende inteiramente do keep-alive para não fazer o visitante esperar 30-60s (`02-RESEARCH.md` Pitfall 4). O intervalo de 5 minutos — e não 14 — é deliberado: schedulers gratuitos têm jitter, e uma janela apertada arrisca deixar o Render dormir (Pitfall 3).

Este plano também abre o caminho crítico de `BRAND-01`: o registro do domínio tem lead time fora do controle do dev (bloqueio registrado em `.planning/STATE.md`), então a ação humana é disparada aqui, no primeiro checkpoint da fase que já toca infraestrutura — não no fim.

Output: Dockerfile publicável, runbook de deploy versionado, backend no ar, schema migrado e cron de keep-alive ativo.
</objective>

`apps/api/Program.cs` lê de configuração, **eagerly e com `?? throw`, antes de `builder.Build()`**:
- `ConnectionStrings:Default` → env var `ConnectionStrings__Default`
- `JWT_SECRET` → env var `JWT_SECRET`
- `Jwt:Issuer` → env var `Jwt__Issuer`
- `Jwt:Audience` → env var `Jwt__Audience`

`apps/api/Program.cs` **não** chama `db.Database.Migrate()` no startup — as migrations são aplicadas fora do processo do app. A migration existente é `apps/api/Data/Migrations/20260814015302_InitialSchema.cs`, criando as tabelas `users`, `cards`, `social_links`, `card_views`.

`apps/api/Program.cs` linha 84 expõe `GET /health` que faz `db.Database.CanConnectAsync()` e responde `{ status: "ok", database: "up" }` com 200, ou `{ status: "error", database: "down" }` com 503. É o alvo do keep-alive: acorda o Render **e**, por consequência da query, o Neon.

Diretório `apps/api` contém: `Api.csproj`, `Api.sln`, `Program.cs`, `Contracts/`, `Data/`, `Endpoints/`, `Services/`, `Properties/`, `Api.Tests/`, `bin/`, `obj/`, `appsettings.json`, `appsettings.Development.json`. O publish de produção deve alvejar `Api.csproj` explicitamente (não a `.sln`, que arrastaria `Api.Tests`).

Restrições travadas no `CLAUDE.md` raiz (não reabrir): Neon e não Supabase (Supabase pausa após 7 dias e exige restauração manual no dashboard); connection string com `SSL Mode=Require;Trust Server Certificate=true` explícito (o default `Prefer` do Npgsql não valida certificado e confunde troubleshooting).

Restrições de `02-RESEARCH.md`: Vercel Cron no plano Hobby é limitado a 1 execução por dia — inutilizável para PUB-04. UptimeRobot teve mudança de ToS (dez/2024) restringindo o plano free a uso não comercial, o que colide com a intenção de monetização da Fase 4. cron-job.org é a escolha primária; workflow agendado do GitHub Actions é o fallback.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → Render (`apps/api`) | Superfície pública completa da API, agora alcançável de qualquer lugar e não só de localhost |

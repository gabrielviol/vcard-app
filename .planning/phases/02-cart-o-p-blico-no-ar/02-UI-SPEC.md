# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase's UI:** the public card page (`/[slug]`), its branded 404 (`app/[slug]/not-found.tsx`), and the "always visible" QR code block added to the existing dashboard edit screen (D-16). Covers `PUB-01, PUB-02, PUB-03, PUB-04, PUB-05, PUB-06, SHARE-01, SHARE-02, BRAND-01`.

**Not in scope (deferred):** WhatsApp button / copy-Pix / `.vcf` download on the public page (Phase 3, `CONT-*`/`PAY-*`), OG image preview (Phase 3, `SHARE-03/04`), view-count analytics (Phase 4, `VIEW-*`), the `is_branded` footer badge itself (Phase 4, `BRAND-02` — this phase only resolves the product's own name/domain, not the footer mark rendered on a card).

**Design system is inherited from Phase 1, not reinitialized.** `components.json` already exists and is confirmed (new-york / zinc / css-variables). This spec extends Phase 1's tokens with the two new surfaces above — it does not introduce new spacing/typography/color tokens.

**Accent color implementation note (read before styling any CTA):** the shadcn Button's `default` variant classes resolve to `bg-primary`, and this project's `--primary` CSS variable (zinc base color) is near-black (`oklch(0.21 0.006 285.885)`), **not** indigo. Phase 1's actual indigo-600 accent (`login/page.tsx:108`, `card-form.tsx:195`) is applied as an explicit Tailwind override on top of the Button component: `className="bg-indigo-600 text-white hover:bg-indigo-700"`. Any new primary/accent CTA in this phase (the 404 page's signup button) must use this exact same override — do not rely on the bare `<Button>` default variant alone, it will render near-black, not on-brand.

**Not covered by shadcn (custom/npm, non-registry):**
- QR code generation — `qrcode` npm package (already locked in root `CLAUDE.md`, re-confirmed in `02-RESEARCH.md`). Flagged `[ASSUMED]` in `02-RESEARCH.md`'s Package Legitimacy Audit — gate behind `checkpoint:human-verify` before `npm install qrcode`. Not a shadcn registry block; ordinary package-legitimacy process applies, not the Registry Safety gate below.
- Social link platform "icon" — no icon at all, by design (see Copywriting/Layout notes below); this mirrors the existing Phase 1 pattern, not a gap to fill with a new icon package.

## Spacing Scale

Declared values (must be multiples of 4) — identical to Phase 1, reused verbatim, no new tokens introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (name→subtitle gap on public card, QR helper caption gap) |
| md | 16px | Default element spacing (subtitle→social-links-list gap) |
| lg | 24px | Section padding (public page horizontal padding on mobile, 404 page padding) |
| xl | 32px | Layout gaps (avatar block → social links list gap on public card) |
| 2xl | 48px | Major section breaks (QR card block top margin within the edit screen) |
| 3xl | 64px | Page-level spacing (top/bottom margin on the public card page on desktop viewports) |

Exceptions (phase-specific fixed dimensions, not part of the abstract scale):
- **QR on-screen size: 240×240px** in the dashboard edit screen (D-16 requires it always visible; this is the concrete size — a multiple of 8, matches `02-RESEARCH.md`'s `QrPreview` example).
- **QR PNG download resolution: 1024×1024px** — already locked in root `CLAUDE.md`, not reopened here.
- **Public page content max-width: 480px, centered**, mobile-first single column; renders full-bleed with 24px horizontal padding under 480px viewport width, and as a centered column with the same 24px internal padding above it.
- **44px minimum touch target** on any icon-only interactive element, per the mobile-first constraint carried over from Phase 1. In Phase 2's actual scope this constraint has no icon-only controls to apply to (QR download actions are labeled buttons, not icon-only — see Layout Notes) — stated here so the constraint isn't silently dropped if Phase 3 adds icon-only controls to this same page later.

## Typography

Identical 4 roles reused verbatim from Phase 1 — no new sizes or weights introduced anywhere in this phase's UI:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Phase 2 usage mapping:
- **Display (28px):** the dono's full name on the public card (the single most prominent element on the page) — and the 404 page's headline, "Esse cartão não existe."
- **Heading (20px):** the "Seu QR code" section title in the dashboard edit screen (new section added this phase).
- **Label (14px/600):** social link platform name on the public card (e.g. "Instagram", "LinkedIn") — matches the existing `text-sm font-semibold` styling already shipped in `social-link-row.tsx:126`, kept visually identical between dashboard and public rendering.
- **Body (16px/400):** the role/company subtitle line under the name (rendered in `text-muted-foreground`/`zinc-600` for hierarchy — no third weight introduced, hierarchy comes from color+role, not a new size), the social link's URL/domain shown as secondary text under the platform label, the QR helper caption ("Aponte a câmera para abrir seu cartão"), and the 404 body copy.

No dedicated "empty state" typography is needed: per D-21, the minimal card (name-only) is a deliberately complete, terminal visual state — it uses the exact same Display name treatment as a fully-filled card, not a smaller/muted/placeholder style.

The two QR download buttons ("Baixar SVG" / "Baixar PNG") use the `outline`/`secondary` Button variant, not accent — the QR itself is the focal point of that block, not a marketing action.

## Layout Notes (supplementary — not a template section, kept for executor precision)

### Public card page (`app/[slug]/page.tsx`)
- Single column, centered, max-width 480px, 24px horizontal padding, mobile-first.
- Vertical order, top to bottom:
  1. Avatar — 96px circle (`size-24`, matches `AvatarPlaceholder`'s existing default). Photo via `<AvatarImage src={photoUrl}>` when `photoUrl` is set, else reuse the existing `components/avatar-placeholder.tsx` (`AvatarPlaceholder`) unchanged — same initials/color logic as the dashboard.
  2. Full name — Display, 8px gap below avatar.
  3. Role/company subtitle — Body, `text-muted-foreground`, format `"{role} · {company}"` when both present, just the one present field alone when only one exists, **omitted entirely (not rendered) when both are empty** — D-19.
  4. Social links list — 32px gap above it; omitted entirely (no container in the DOM) when there are zero links — D-19. When present: each row full-width, bordered (`rounded-lg border border-zinc-200 bg-white p-3`, matching `social-link-row.tsx`'s existing visual style for continuity), platform name in Label style, URL/domain in Body/muted style below it, minimum 44px row height, tapping opens the link in a new tab.
  5. Nothing else in Phase 2 — no WhatsApp button, no Pix copy, no `.vcf` download, no footer brand mark (all later phases).

### QR block (dashboard edit screen, `app/(dashboard)/dashboard/cards/[id]/edit/page.tsx`)
- Always visible (D-16) — its own `Card` block titled "Seu QR code" (Heading), placed after the existing social-links section so it doesn't interrupt the identity/contact/Pix editing flow.
- QR image: 240×240px, `<img src="/{slug}/qr">` (SVG for on-screen crispness), centered, `zinc-200` border, white background — never tinted, never inverted, D-18.
- Below the QR: helper caption (Body, muted), then two `outline`/`secondary`-variant buttons side by side (stack vertically under ~360px width): "Baixar SVG" and "Baixar PNG", each pointing at `/{slug}/qr?download=1` (and `?format=png&download=1` for the PNG variant).

### 404 page (`app/[slug]/not-found.tsx`)
- Same centered/480px/24px-padding shell as the public card page, for visual family resemblance (D-22).
- Vertical order: small product wordmark at top ("Vizzo" — provisional per D-14) → Display headline → Body explanation → single accent-colored CTA button, no secondary/ghost "back" link (D-23 — one clear acquisition path, not diluted by an escape hatch).
- Must be a plain, non-streamed Server Component with no `loading.tsx` above it in the segment tree (see `02-RESEARCH.md` Pitfall 2) — this is an implementation constraint, not a visual one, but it directly affects whether `curl -I` on a dead slug returns a true `404` status; flagged here so the executor doesn't accidentally violate it while building the page shell.
